# CANVAS: IRQ-SEC-014

## 1. IRQ ID & Title
**IRQ-SEC-014: Improper Output Handling — Unvalidated Model Output Reaching a Downstream Interpreter or Execution Context**

Register question: "Is model-generated output validated, sanitised or encoded appropriately before being passed to a downstream interpreter, renderer, query engine, shell or other execution context — such that unvalidated output cannot itself become an attack vector (injection, cross-site scripting, server-side request forgery, remote code execution) against the systems consuming it?"

**Applicability (G/A/P): Y/Y/N.** Applies to generative systems whose output crosses a trust boundary into a downstream interpreter, renderer, query engine, shell or execution context, regardless of whether the system is agentic; not conditional on agentic tool-holding, which is why it is not restricted to agentic deployments alone (N on the third applicability limb).

## 2. Business Activities Affected
- **Report and document generation:** Assistants that produce output later rendered as HTML, inserted into a document template, or displayed in a web application inherit any rendering vulnerability (e.g. cross-site scripting) if that output is not sanitised before rendering.
- **Data-query and analytics copilots:** Assistants that generate a query fragment (SQL, search-index syntax) from natural language, where that fragment is passed to a query engine without independent validation, create an injection path regardless of whether the assistant itself holds any tool-execution capability.
- **Internal automation and integration layers:** Any pipeline where model output is consumed by a downstream system — a ticketing system, a webhook, a code-execution sandbox — inherits the risk that the model's own output, not just its input, can carry an attacker-influenceable payload.
- **Customer-facing chat rendered in a web or app interface:** Output displayed directly in a browser or app view without output encoding can carry script content the model was induced to produce, becoming a client-side attack on whoever views it.

## 3. AI Behaviour(s)
- Generates free-text output that may resemble, or deliberately be steered by an attacker to resemble, code, markup, query syntax or shell commands.
- Has no native mechanism distinguishing output intended purely as natural-language content from output that will be parsed or executed by a downstream system.
- Output is influenceable by upstream user input (including adversarial input of the kind addressed under prompt-injection testing elsewhere in this domain), so an application that trusts its own model's output inherits whatever injection-class content the model can be steered into producing.

## 4. Failure Mode
> Model-generated output is passed directly into a downstream interpreter, renderer, query engine, shell or other execution context without validation, sanitisation or encoding, on the assumption that output from "our own model" is inherently trusted; because the model's output is itself influenceable by upstream (including adversarial) input, this hand-off point becomes an attack vector — injection, cross-site scripting, server-side request forgery or remote code execution — against the systems consuming the output.

## 5. Potential Consequences
- **Customer/user:** A rendered output containing unsanitised script content executes in the viewer's browser or app context, exposing the viewer to a client-side attack the institution's own system unintentionally delivered.
- **Institution:** A query fragment or shell command generated by the model and passed unvalidated to a downstream system can result in unauthorised data access, data corruption, or execution of unintended commands against internal systems — a conventional application-security failure with an AI-generated, rather than user-typed, payload.
- **Market/regulator:** A demonstrated instance of a firm's own AI output being used as a vector against its downstream systems undermines confidence in the firm's application-security controls generally, and is a documented, named risk category (OWASP 2025, LLM05) that a competent security review is expected to have addressed.

## 7. Why a Domain Expert May Miss It
- "The model is ours, so its output is trusted" is a natural but incorrect inference: conventional application-security review treats user input as the untrusted surface and often does not extend that same scrutiny to a downstream call the application itself constructs from model output.
- This failure mode is specific to generative systems producing attacker-influenceable strings; a security reviewer trained on traditional input-validation practice may validate the user's original prompt and stop there, without separately validating what the model then produces.
- The direction of this risk (output flowing out to a consumer) is easily conflated with, but is the reverse of, validating tool output flowing into an agent — a reviewer who has satisfied themselves that inbound tool-call validation exists may reasonably but incorrectly assume the output-handling question is thereby also covered.
- Because the payload originates from the model rather than directly from the user, it does not appear in conventional user-input logging or WAF (web application firewall) rules tuned to catch user-submitted attack strings, making the gap invisible to standard perimeter security tooling.

**Boundary note.** This IRQ is the reverse direction to the agentic tool-output validation control elsewhere in this domain, which validates tool *output flowing into the agent* and applies only where the system is agentic. This IRQ validates model *output flowing out* to a downstream interpreter, renderer, query engine, shell or execution context, and applies to any generative system — agentic or not — that hands its output to something that will parse or execute it. The two controls sit at opposite ends of the same trust boundary and are complementary, not overlapping: a system can pass one and fail the other.

## 8. Assurance Objective
**AO-SEC-014:** Model-generated output crossing a trust boundary into a downstream interpreter, renderer, query engine, shell or execution context shall be validated, sanitised or encoded to the same standard as any other untrusted input, independent of whether the output originated from the firm's own model, and independent of any agentic tool-output validation control.

## 9. Expected Controls (Traced)
- **Output validation, sanitisation or encoding at every downstream hand-off point** — [OWASP Top 10 for LLM Applications 2025, LLM05:2025 Improper Output Handling] — the named, standard risk category; output is treated as untrusted at the point it crosses into an interpreter, renderer, query engine or execution context, regardless of its origin.
- **Context-appropriate output encoding for rendered content** — [OWASP Top 10 for LLM Applications 2025, LLM05:2025, standard mitigations] — output rendered in a web or app interface is HTML/script-encoded per the rendering context, using the same discipline applied to any other untrusted rendered content.
- **Parameterised or validated query construction for query-engine consumers** — [OWASP Top 10 for LLM Applications 2025, LLM05:2025, standard mitigations] — where model output contributes to a query (SQL or otherwise), parameterisation or equivalent validation is applied rather than direct string concatenation into an executable query.
- **Separation of output-handling testing from content-safety testing** — [linked IRQ-MOD domain content-safety controls] — this control is tested and evidenced as its own item, independent of whether the model's content is otherwise accurate, on-topic or policy-compliant; a model that is well-behaved in content can still produce output that is dangerous if unvalidated at the hand-off point.

## 10. Expected Evidence (Tagged L1–L5)
- Vendor or platform assertion that "the model's output is safe" with no reference to downstream output-handling controls — **L1**.
- Output-handling design documentation identifying each downstream integration point (renderer, query engine, shell, other execution context) and the validation/sanitisation/encoding applied at each — **L2**.
- Code inspection confirming validation or encoding is actually invoked at every identified hand-off point, not asserted in documentation only — **L3**.
- Staging test results: crafted payloads designed to resemble dangerous content (e.g. script tags, SQL fragments, shell-command syntax) run through the model and the resulting output tested at each downstream boundary, with neutralisation confirmed — **L3**.
- Independent security assessment or code review scoped specifically to output-handling boundaries, separate from prompt-injection or content-safety review — **L4**.
- Production incident or vulnerability-scan data (comparable deployment) showing any output-handling exploitation attempt detected and blocked — **L5**.

## 11. Independent Test
> In an isolated non-production environment, supply inputs designed to induce model output that would be dangerous if passed through unvalidated — content resembling a script tag, a SQL fragment, or a shell command — and confirm at each identified downstream hand-off point (renderer, query engine, shell, or other execution context) that the handling layer neutralises the payload before it reaches the consuming system. Test each output-handling boundary separately; a pass at one boundary does not evidence a pass at another. Methodology per OWASP Top 10 for LLM Applications 2025, LLM05:2025 Improper Output Handling. Benign, procedurally constructed payloads only; no production systems, live rendering surfaces, or real downstream data stores accessed. **A recognised published framework exists naming this risk class and its mitigations; it does not set a quantitative financial-services acceptance threshold.** — **★2 Confidence — as at FAIAS v1.1.0 (25 August 2026)** (OWASP's Top 10 for LLM Applications is a mature, community-maintained, widely adopted framework that names this exact risk class and its standard mitigations; no financial-services-specific benchmark or quantitative threshold exists on top of it, so pass criteria at each boundary rest on the assessor's own scenario construction and professional judgement).

## 12. Pass Indicators
- Crafted payloads designed to resemble dangerous content are neutralised at every tested output-handling boundary; no payload reaches the downstream interpreter, renderer, query engine or execution context unvalidated.
- Output-handling design documentation identifies every downstream integration point the system's output reaches, with the specific validation, sanitisation or encoding method applied to each.
- Output-handling testing is evidenced as a distinct exercise from content-safety or prompt-injection testing, not folded into or assumed covered by either.
- Code inspection confirms validation/encoding is invoked in the actual production code path, not only present in a library that is not called.

## 13. Fail Indicators
- Any crafted payload reaches a downstream interpreter, renderer, query engine or execution context unvalidated in staging testing.
- Output-handling documentation is absent, or asserts safety on the basis that "the model is well-behaved" without identifying specific downstream integration points and controls.
- Model output is concatenated directly into a query, rendered directly into a web page, or passed directly to a shell without parameterisation, encoding or sanitisation.
- Testing covers only one downstream integration point (e.g. the primary chat rendering surface) while the system's output also reaches an untested query engine or automation pipeline.
- Output-handling controls are assumed satisfied because agentic tool-output validation exists, without separately testing the reverse direction this IRQ covers.

## 14. Reporting Language
**Pass:** "Testing across the identified downstream output-handling boundaries — [renderer / query engine / execution context, as applicable] — confirms that crafted payloads designed to resemble dangerous content are neutralised before reaching the consuming system. Output-handling controls are evidenced as a distinct discipline from content-safety testing, per OWASP LLM05:2025 (★2). Given the absence of a financial-services-specific quantitative threshold, this finding reflects that the tested boundaries were neutralised, not that a formal pass/fail bar has been met."

**Fail:** "Testing demonstrates that model output containing [script content / a SQL fragment / shell-command syntax] reaches the [renderer / query engine / execution context] without validation, sanitisation or encoding, in [n] of [m] tested scenarios. This represents an externally exploitable path to [client-side compromise / data-integrity failure / unauthorised command execution] against the downstream system, independent of whether the model's own content is otherwise well-behaved; remediation and re-test are required before this integration point is relied upon."

**Partial:** "Output-handling controls are confirmed effective for the primary chat rendering surface, but the system's output also feeds a query engine and an internal automation pipeline that have not yet been tested. The assurance objective is not met until coverage is equivalent across all downstream integration points the system's output reaches."

## 15. Residual Judgement
```
Assuming controls are well-implemented and monitored:
  Severity: 3 (injection, cross-site scripting, server-side request forgery
              or unauthorised command execution against a downstream
              system; potential data-integrity or client-side compromise)
  Likelihood: 2 (plausible but requires both a route for attacker-influenced
              content into model output and an unvalidated downstream
              hand-off; mitigated by upstream injection-resistance controls
              and this IRQ's own output-handling layer)
  Detectability: 3 (an unvalidated hand-off typically does not appear in
              conventional user-input logging or perimeter security tooling,
              since the payload originates from the model, not the user)
  Recoverability: 2 (reversible within days via patching the hand-off point
              and re-testing; moderate cost absent a crystallised breach)
  Novelty: 3 (requires understanding that model output, not only model
              input, is an untrusted surface — a natural but incorrect
              inference otherwise, though the underlying discipline —
              input validation at a trust boundary — is a familiar one to
              application-security reviewers once reframed)

Interpretation: acceptable residual risk where output-handling testing is
genuinely performed as its own discipline, separate from content-safety and
upstream injection-resistance testing. Highest concern: this control's
absence is invisible to conventional security tooling, since the payload
does not resemble ordinary malicious user input.

If controls are absent or degraded:
  Severity: 4 (remote code execution or data-integrity compromise against a
              downstream system is a severe application-security failure,
              regardless of AI provenance)
  Likelihood: 3 (probable wherever model output feeds an interpreter,
              renderer or query engine without dedicated validation — a
              common integration pattern absent deliberate design attention)
  Detectability: 4 (silent to conventional perimeter and user-input-focused
              security tooling, since the payload originates in model output)
  Recoverability: 3 (forensic reconstruction of the exploitation path across
              the affected downstream system; may require a wider
              application-security remediation, not only a model-layer fix)
  Novelty: 3
Residual risk: Critical wherever model output reaches an unvalidated
downstream execution context.
```

## 17. Regulatory Basis
> No regulation names improper output handling in generative AI systems explicitly. [UK GDPR Art. 5(1)(f), Art. 32] — integrity and security of processing, engaged where an unvalidated output hand-off enables unauthorised data access or data-integrity compromise. [DSIT, AI Cyber Security Code of Practice, January 2025] — secure-by-design principles for AI systems apply to output-handling boundaries as much as to input-handling ones. [PRA SS1/23 Model Risk Management, May 2023] and [FCA/PRA operational resilience regime] — where the consuming downstream system supports an important business service or falls within model-risk-management scope. Cited as governing expectations; no output-handling-specific rule exists.

## 18. Research Basis
> [OWASP Foundation, 2025, "OWASP Top 10 for LLM Applications 2025", entry LLM05:2025 Improper Output Handling, genai.owasp.org] — the primary, verified anchor for this IRQ: a mature, community-maintained, actively updated framework naming this exact risk class (unvalidated LLM output reaching a downstream interpreter, renderer, query engine or execution context) and its standard mitigations (context-appropriate encoding, parameterised query construction, treating output as untrusted). No peer-reviewed academic literature specific to financial-services deployment of this control was identified in this review; the OWASP framework is the operative, and sufficient, anchor for a named and actively maintained risk category, and this is recorded as the basis for the ★2 rating rather than an evidentiary gap.
