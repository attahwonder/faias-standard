# TP-GOV-014 — AI Failure-Class Coverage in the Incident Taxonomy

## 1. Procedure Identity
**Procedure ID:** TP-GOV-014
**IRQ:** IRQ-GOV-014 — Incident Taxonomy Without AI-Specific Failure Categories
**Assurance objective:** AO-GOV-014 — The firm's incident classification scheme shall recognise AI-specific failure classes — at minimum mass confabulation, prompt-injection compromise, agentic misaction, and silent bias event — with defined severity mapping and a regulator-notification route for each, such that an AI-specific event can be classified and the notification clock can start.
**★ Confidence (carried from canvas, unchanged):** ★2 — DORA and SUP 15.3 supply a credible, binding classification-and-notification architecture to test against, but **no published methodology defines AI-specific incident-category adequacy**, and the walk-through's coverage of only one class per exercise means residual classes are assessed by documentation review alone, not exercised.
**Method classification:** Emerging Practice / bespoke — a documentation-and-walkthrough exercise, professional-judgement-led, for which the canvas records that no published protocol exists. The **architecture it is run against** is binding and mature: DORA (Regulation (EU) 2022/2554) Art. 17 (ICT-related incident management process), Art. 18 and its classification Regulatory Technical Standards (six criteria with materiality thresholds), and Art. 19 (three-report notification structure); and FCA SUP 15.3.1R for the UK notification route. **The four AI-specific category definitions themselves are Emerging Practice** — the canvas records that no published incident-taxonomy standard defines them and that they have no external precedent; DORA and SUP 15.3 supply the architecture the categories must be added to, not the categories.

## 2. Preconditions
**Environment:** Governance documentation and a desk-based tabletop exercise only. **No production system access is required**, and none is taken. The tabletop uses a hypothetical event constructed by the reviewer; no real incident record is altered and no notification is triggered.
**Scope bound, stated before the procedure runs and carried into the report.** This procedure tests **only** whether the existing incident classification scheme's category list has AI-specific entries with defined severity mapping and notification routing. It does **not** test whether incident management, a severity matrix or notification processes exist at all — that is a separate, non-AI-specific control assessed elsewhere. A firm can pass this and have weak incident management; it can fail this and have strong incident management. Reporting must not let one stand for the other.
**Access required:** The incident taxonomy documentation listing all defined categories, with severity mapping and notification routing shown for each; the severity matrix and its basis; the DORA Art. 18 classification criteria as the firm applies them, or the firm's documented equivalent; the notification-procedure documentation covering the DORA Art. 19 three-report structure and the FCA SUP 15.3.1R route, as applicable to the entity; the incident register for the review period, for the historical-event limb; any internal audit or independent review of the taxonomy.
**Artefacts required:** The taxonomy category list in full; severity-mapping definitions per category; notification-route definitions per category; the DORA Art. 18 classification criteria as applied, or the documented equivalent; the incident register, so that any actual historical AI-specific event can be traced to how it was in fact classified.
**Personnel required:** Reviewer (lead); the operational-resilience or incident-management owner of the taxonomy; the regulatory-notification or regulatory-liaison owner; **a participant with AI-specific technical competence for the tabletop**, because the walk-through's value depends on whether the room can recognise the simulated event as the class it is.
**Data handling:** Incident register entries may name individuals, customers or counterparties. Handle under engagement confidentiality and report by incident reference and class rather than by content in wider circulation.

## 3. Test Design
**A documentation review against four named classes, supplemented by one tabletop walk-through.** The canvas defines the test as exactly this; there is no system-behaviour limb and none is constructed.

**Documentation limb.** For each of the four named AI failure classes — **mass confabulation, prompt-injection compromise, agentic misaction, silent bias event** — establish whether the taxonomy contains a distinct category, or an **explicit, reasoned mapping** onto an existing category. In both cases, establish whether severity mapping and a notification route are defined.

Three of the four classes produce **no conventional error state**: the system is available, responsive and throwing no exceptions throughout. That is why a taxonomy-completeness review conducted against the taxonomy's own historical categories will not surface the gap, and why this procedure works from an externally supplied class list rather than from the firm's own.

**Mapping-quality assessment, not merely mapping existence.** Where a class is mapped onto an existing category rather than given its own, assess whether the fit is structural or forced. The canvas's fail indicator names a poor structural fit specifically — mass confabulation force-fitted into a "data quality" category with no severity or notification consequence appropriate to a customer-facing failure. Agentic misaction conflated with a conventional "unauthorised transaction" category built around a human actor is the same defect: the actor is the system acting on its own tool permissions, which changes both root-cause investigation and remediation. Prompt-injection compromise mapped to "unauthorised access" is a third: the injection mechanism, evidence trail and appropriate response all differ materially.

**Severity-mapping basis.** Establish whether severity mapping for AI-specific categories references the DORA Art. 18 classification criteria — clients and counterparts affected and reputational impact; duration and downtime; geographical spread; data losses across availability, authenticity, integrity and confidentiality; criticality of services affected; economic impact — or the firm's documented equivalent, rather than a generic high/medium/low scale untethered to those criteria.

**Tabletop limb.** One class, **selected by the reviewer after the documentation limb is complete**, is traced as a hypothetical event through classification, severity mapping and notification routing, to identify where the taxonomy is silent or ambiguous. The class chosen is the one where the documentation is weakest or most ambiguous — the tabletop is a probe, not a demonstration. The selection and its rationale are recorded before the exercise begins.

**Historical limb.** Where the incident register contains an actual AI-specific event, trace how it was in fact classified and whether classification and notification, if applicable, were timely and correctly routed. This is the domain's "existence is not operation" discipline: a taxonomy entry that has never classified anything has never been shown to work. Where no historical event exists, the absence is recorded rather than treated as a pass.

**Coverage limitation, stated in the report.** The tabletop exercises one class. The other three are assessed on documentation alone. The canvas makes this an explicit component of the ★2 rating, and the report must carry it rather than implying all four were exercised.

## 4. Steps
1. Record the scope bound and confirm with the taxonomy owner that the procedure is not assessing incident management, the severity matrix or notification processes generally.
2. Obtain the taxonomy documentation in full, with severity mapping and notification routing shown per category. **Record:** the complete category inventory as it stands.
3. For each of the four named AI failure classes, establish whether a distinct category exists. **Record:** present as a distinct category / mapped onto an existing category / silent.
4. Where a class is mapped rather than distinct, assess the fit. **Record:** the existing category used, and the reviewer's assessment of whether the fit is structural or forced, with reasoning — this is the judgement the ★2 rating rests on and it must be exposed.
5. For each of the four classes, establish whether severity mapping is defined, and whether it references the DORA Art. 18 criteria or the firm's documented equivalent rather than a generic scale. **Record:** the mapping and its reference basis, or its absence.
6. For each of the four classes, establish whether a notification route is defined, referencing DORA Art. 19 report stages and/or FCA SUP 15.3.1R as applicable to the entity. **Record:** the route, or its absence.
7. Select the tabletop class after step 6, choosing the class where documentation is weakest or most ambiguous. **Record:** the class selected and the selection rationale, before the exercise begins.
8. Run the tabletop: trace a hypothetical event of that class through classification, severity mapping and notification routing with the taxonomy owner, the notification owner and the AI-competent participant present. **Record:** where the taxonomy is silent, where it is ambiguous, every dead end, and whether the participants agree on how the event would be classified and whether DORA/SUP 15.3 notification would trigger.
9. Search the incident register for any actual AI-specific event in the review period. **Record:** how it was in fact classified, whether the classification was correct, and whether any notification was timely and correctly routed — or that no such event has occurred.
10. Review any internal audit or independent review of the taxonomy scoped to AI-specific coverage. **Record:** its existence and findings, or its absence.

## 6. Interpretation (per CANVASES_GOV.md fields 12–14)
**Pass** where all four named AI-specific failure classes appear in the taxonomy either as distinct categories or with an explicit, reasoned mapping onto an existing category, in both cases with defined severity mapping; each has a defined notification route referencing DORA Art. 19 report stages and/or FCA SUP 15.3.1R as applicable; the tabletop walk-through completes without identifying an ambiguity that would delay classification or notification for the exercised class; severity mapping references the DORA Art. 18 classification criteria or the firm's documented equivalent rather than a generic scale; and at least one historical AI-specific event evidences correct, timely classification.

**Fail** where: one or more of the four named classes has no category and no explicit mapping — the taxonomy is silent on it; **or** a mapping exists but is a poor structural fit, with no severity or notification consequence appropriate to the failure; **or** the tabletop surfaces genuine ambiguity or a dead end, with participants unable to agree how the simulated event would be classified or whether it would trigger DORA/SUP 15.3 notification; **or** severity mapping for AI-specific categories is not referenced to the DORA Art. 18 criteria or any equivalent structured basis; **or** a historical AI-specific event is found to have gone unclassified or misclassified, with a corresponding delay to notification.

**Partial** where — the canvas's own shape — two classes are recognised as distinct categories with defined severity mapping and notification routing, a third is mapped onto an existing category without AI-specific severity guidance, and a fourth has no category or mapping at all. The assurance objective is not met for the latter two; remediation should add or adequately map the missing categories. Report class by class; a proportion across four classes is not actionable.

## 7. Evidence Outputs
- Statement that the firm has an incident classification scheme — **L1** (asserts a scheme exists; does not evidence AI-specific category coverage)
- Incident taxonomy documentation listing all defined categories, with severity mapping and notification routing shown for each — **L2**
- Documentation review confirming, class by class, whether the four AI-specific failure classes appear as distinct categories or are explicitly and adequately mapped, with severity and notification routing defined — **L3**
- Reviewer's mapping-quality assessment with reasoning, where a class is mapped rather than distinct — **L3**
- Severity-mapping basis assessment against the DORA Art. 18 criteria or the firm's documented equivalent — **L3**
- Tabletop walk-through record for the selected class, tracing classification, severity mapping and notification routing, with gaps and ambiguities recorded and the selection rationale — **L3**
- Internal audit or independent review of the taxonomy against DORA Art. 17/18 classification requirements and SUP 15.3 notification triggers, specifically for AI-specific coverage — **L4**
- Historical AI-specific event trace showing how it was in fact classified, and whether classification and notification were timely and correctly routed — **L5**

## 8. Common Pitfalls & Limitations
- **Reviewing the taxonomy against itself.** A completeness review conducted against the taxonomy's own historical categories cannot surface a class that has no analogue in them. The externally supplied four-class list is the instrument.
- **Accepting any mapping as adequate.** Prompt-injection compromise looks, to a reviewer without AI-specific training, like an "unauthorised access" event already covered — obscuring that the injection mechanism, evidence trail and appropriate response differ materially. Assess the fit, not the existence.
- **Conflating agentic misaction with unauthorised transaction.** The conventional category is built around a human actor circumventing controls. Here the actor is the system acting on its own tool permissions, which changes both the root-cause investigation and the remediation.
- **Expecting an error state.** Mass confabulation and silent bias events produce no alert, exception or malfunction; the system is available and responsive throughout. An incident-detection mindset trained to look for system failure will not flag them as candidate incidents at all, which is why the taxonomy review must ask about them by name.
- **Generic severity scales.** A high/medium/low scale untethered to the DORA Art. 18 criteria does not meet the canvas's pass indicator.
- **Running the tabletop on the easiest class.** Select after the documentation limb, and select where the documentation is weakest. A walk-through of the one class the taxonomy handles well is a demonstration, not a probe.
- **Running the tabletop without AI-specific competence in the room.** If nobody present can recognise the simulated event as the class it is, the exercise measures the room, not the taxonomy.
- **Implying all four classes were exercised.** One was. Three were reviewed on documentation. The canvas makes this coverage limit part of the rating, and the report carries it.
- **Letting this finding stand for incident-management capability.** The scope bound is narrow and deliberate: this tests the category list. A pass here says nothing about whether the firm responds to incidents well, and the canvas's own Pass language says so in terms.
- **Regulatory-scope limitation carried forward.** The canvas records that **no US or macroprudential regulatory anchor requiring AI-specific incident categorisation was identified**, and that testing under this IRQ is therefore scoped to the DORA/SUP 15.3 UK/EU framework. Where the entity is not within DORA scope, state which architecture the test was run against.
- **★2 caveat.** A bespoke documentation-and-walkthrough exercise with no published protocol, and four category definitions with no external precedent. Report as professional assessment of **taxonomy coverage**, not of the firm's broader incident-management capability, which this procedure does not test.

## 9. Time / Effort Estimate
**3 reviewer-days**: 0.5 day taxonomy extraction and scope confirmation; 1 day class-by-class coverage, mapping-quality and severity-basis assessment across the four classes, with the notification-route cross-reference against DORA Art. 18/19 and SUP 15.3.1R; 0.5 day tabletop preparation, selection and facilitation; 0.5 day historical-event trace through the incident register; 0.5 day analysis and working papers. Firm-side participant time for the tabletop is additional, typically half a day across three or four participants.
